# System design and tradeoffs

## 1. Overview

Four layers, all in one Kubernetes namespace (`urumi`) and one Helm release:

1. **Store:** WordPress and WooCommerce on MariaDB, with persistent volumes.
2. **WooCommerce MCP server:** exposes products and orders as MCP tools.
3. **Gateway and dashboard:** a FastAPI service that is an MCP client to every registered upstream and an MCP
   server for the team, plus a React dashboard.
4. **Chat agent:** an LLM tool loop inside the gateway.

Two extra, tiny upstreams (`notes`, `time`) make three upstream servers in total.

## 2. Components

| Component | Kind | State | Notes |
|---|---|---|---|
| `mariadb` | StatefulSet | PVC | WordPress database |
| `wordpress` | Deployment, strategy `Recreate` | PVC | One replica; a ReadWriteOnce volume cannot be shared by two pods |
| `wp-init` | Helm hook Job (post-install, post-upgrade) | none | WP-CLI: installs and updates WordPress and WooCommerce to the pinned versions, sets permalinks, currency, cash on delivery and free shipping, and inserts the WooCommerce API key |
| `woo-mcp` | Deployment | none | MCP server over the WooCommerce REST API |
| `notes-mcp`, `time-mcp` | Deployments from one generic template | none (notes keeps data in memory) | A new server needs one entry in `values.yaml` |
| `postgres` | StatefulSet | PVC | Users, API key hashes, upstream registry, audit log, tool permissions |
| `gateway` | Deployment | none | Admin API, `/mcp`, chat agent |
| `dashboard` | Deployment | none | nginx serving the built React app |
| Traefik | k3s bundled ingress controller | none | `/api` and `/mcp` go to the gateway, `/` to the dashboard, the store host to WordPress |

Every workload has readiness and liveness probes and resource requests and limits (values in `values.yaml`).

## 3. Architecture choices and tradeoffs

**One Helm chart, values per environment.** One chart is easy to reason about and to roll back as a unit.
The tradeoff is that everything is released together; there is no per-component release.

**k3d locally, k3s on a VPS.** Both are k3s, so Traefik, the local-path storage class and the NetworkPolicy
controller behave the same. `kind` would not enforce NetworkPolicies by default.

**WooCommerce MCP server talks to the REST API (not WP-CLI).** The REST API is documented, versioned and plain
HTTP, and the MCP server needs no access to the WordPress filesystem or to `kubectl exec`, which keeps the isolation
between pods intact. WP-CLI would need a shared volume or exec rights. The tradeoff is that WooCommerce only
accepts key and secret as Basic Auth over HTTPS. Inside the cluster the traffic is HTTP, so the MCP server sends
`X-Forwarded-Proto: https`; the chart's `wp-config` snippet then makes WordPress treat the request as secure. A side
effect is that WordPress builds `https://` links, which the MCP server rewrites to the public store URL. The
server also returns only what a tool needs: an order has the customer's name but not the email, phone or address
(data minimisation).

**MCP Python SDK pinned below 2.** The current SDK line (2.x) renamed the server class and changed the API, so the
project pins `mcp>=1.28,<2`. Migrating is possible later.

**Stateless Streamable HTTP everywhere.** Every MCP request is independent (`stateless_http`, JSON responses), so
no session affinity is needed behind several replicas. The cost is that the gateway opens a fresh MCP session to
the upstream for every tool call (initialize, then call). That is simple and robust but adds latency; pooling
would be the next optimisation.

**Postgres for the gateway.** Users, key hashes, the registry, the audit log and permissions need transactions
and queries (audit filters). Tables are created at startup with `create_all`, which only adds tables. A real
migration tool would be needed for schema changes.

**Authentication.** Dashboard: a signed `HttpOnly`, `SameSite=Lax` cookie, and the user is loaded from the database
on every request, so deactivating a user cuts the session at once. MCP clients: `Authorization: Bearer umk_...`.
Keys are random (256 bit) and stored as SHA-256 hashes, which is enough because they are not guessable (passwords
use scrypt). A key is checked against the database on every request, so a revoked key is rejected on the very next
call.

**The chat agent lives in the gateway.** It calls the same `execute_tool` function as `/mcp`, with the logged-in
user's identity. Routing, timeouts, permissions, error messages and audit are therefore identical, and "which user
did this" has one answer. The LLM key is a Kubernetes Secret outside Helm. The provider is any OpenAI-compatible
API (Groq here: `openai/gpt-oss-120b` first, `openai/gpt-oss-20b` as fallback).

**Secrets are generated by Helm and reused.** Passwords, the session secret, the Fernet key and the WooCommerce API
key are random on first install, and `lookup` returns the same values on later upgrades. Nothing secret is in the
repository. The limitation: `lookup` does not work with `helm template`, so a GitOps tool that renders with
`helm template` would regenerate them (use sealed secrets or an external secret manager there).

**NetworkPolicy: deny by default.** One default-deny policy for the namespace, one policy for DNS, and one
allow-list per component (see `templates/networkpolicy.yaml`).

## 4. Request flows

### An external MCP client calls a tool

1. The client sends `POST /mcp` with `Authorization: Bearer <key>`.
2. Traefik routes `/mcp` to the gateway. The gateway hashes the key and finds it in Postgres. A revoked key, an
   unknown key or an inactive user gives `401`.
3. `tools/list`: the gateway returns the aggregated list for the user's role (section 5).
4. `tools/call woocommerce__list_orders`: the gateway splits the name at the first `__`, finds the server, checks
   the permission, decrypts that server's stored credential, and calls the upstream's `/mcp` with the credential as
   its **own** header. The client's key is never forwarded.
5. The upstream (`woo-mcp`) calls the WooCommerce REST API and answers. The gateway writes an audit row (user, server,
   tool, duration, outcome) and returns the result.

### A chat message

1. The dashboard sends the conversation to `POST /api/chat` with the session cookie.
2. The gateway lists the user's tools, builds the model request (system prompt with the current date, history,
   tools), and calls the LLM.
3. If the model asks for tools, each call goes through `execute_tool` (steps 4 and 5 above, with source `chat`),
   and the result (capped at 6000 characters) goes back to the model. This repeats up to 6 steps.
4. The final answer and the list of tool calls (name, arguments, result preview, duration) go back to the dashboard.

## 5. Tool aggregation, routing and failure handling

**Naming and collisions.** A tool is exposed as `<server>__<tool>`. Server names are limited to lowercase letters,
digits and hyphens, so the first `__` is always the separator. Two servers can therefore both have `server_info`:
they become `notes__server_info` and `time__server_info`. Routing splits at the first `__`, so even a tool whose own
name contains `__` still works.

**Listing.** Every enabled server is probed in parallel (`asyncio.gather`). Each probe does the URL check, the MCP
handshake and `tools/list` inside one timeout (5 s). The result is cached for 10 s per server (and the cache is
dropped when the server is edited). Disabled and unreachable servers contribute no tools.

**Slow or dead upstream.**

* A listing never waits for a dead server longer than the probe timeout, and one server's error is caught inside its
  own probe, so the others are unaffected.
* A tool call has its own timeout (30 s). A failure becomes a clear message such as
  `Upstream 'time' failed: timed out after 30s` or `... cannot connect ...`. The message never contains
  credentials or tracebacks.
* The dashboard shows Connected, Unreachable (with the reason) or Disabled. Status is refreshed every 15 s in the
  browser; the server-side cache is 10 s, so a killed pod shows as unreachable within about 25 s, or immediately
  with **Refresh status**.

**Disable and remove.** The tool call path reads the server row from the database, not the cache, so a disabled
server rejects calls at once (outcome `denied`) and its tools vanish from the list for every client and for the
chat agent.

**Permissions.** A deny-list per role (`tool_denials`). A blocked tool is left out of the member's tool list and is
rejected on a direct call. Admins are never restricted, so nobody can lock out all admins. A new tool that an
upstream adds later is allowed for members until an admin blocks it.

**Audit.** Every call writes: user, server, tool, time, duration, outcome (`success`, `error`, `denied`) and the
source (`mcp` or `chat`). If the audit write fails, the call is not blocked, and the failure is logged (fail open).

**Untrusted text.** Tool descriptions from an upstream are stripped of control characters, capped (500 characters
in the tool list) and prefixed with `[server]`. See the threat model.

## 6. Data model (Postgres)

* `users`: email, name, role (`admin` or `member`), scrypt password hash, `must_change_password`, `active`.
* `api_keys`: owner, name, display prefix, SHA-256 hash, `last_used_at` (written at most once a minute), `revoked_at`.
* `mcp_servers`: unique name, URL, `enabled`, auth type (`none`, `bearer`, `header`), header name, Fernet-encrypted credential.
* `audit_log`: time, user id and email, server, tool, duration, outcome, error, source.
* `tool_denials`: (role, server, tool), unique.

## 7. Kubernetes layout

* **Secrets:** `urumi-store-db`, `urumi-store-admin`, `urumi-woo-api`, `urumi-gateway` (all generated by Helm) and
  `urumi-llm` (created by hand).
* **Volumes:** MariaDB, WordPress and Postgres each have a PersistentVolumeClaim (storage class from `storageClass`).
* **Ingress:** the store host goes to WordPress. The app host sends `/api` and `/mcp` to the gateway and everything else
  to the dashboard (longest prefix wins). The MCP servers and databases have no Ingress and ClusterIP services only.
* **Security context:** the gateway, the three MCP servers and the dashboard run as non-root users with a read-only
  root filesystem, no privilege escalation and all capabilities dropped. WordPress, MariaDB and Postgres use their
  images' defaults.
* **Network:** see `templates/networkpolicy.yaml`. In short: Traefik reaches the dashboard, the gateway and
  WordPress; the gateway reaches Postgres, the three MCP servers and the public internet (80 and 443 only, never
  private ranges or the cloud metadata address); `woo-mcp` reaches only WordPress; WordPress reaches only
  MariaDB and the public internet; nothing else is allowed.

## 8. What changes for production

Only Helm values, and a few steps outside the chart (README, section on the VPS).

| Topic | Local | Production |
|---|---|---|
| **DNS** | `*.localtest.me` resolves to 127.0.0.1 | A records for the store and app hosts point to the server |
| **Ingress** | k3d maps host ports 80 and 443 to the bundled Traefik | k3s's bundled Traefik is exposed on the server's ports 80 and 443 |
| **TLS** | none | `https` in the values, an Ingress `tls:` section, and certificates from cert-manager (created outside the chart); the session cookie becomes `Secure` automatically |
| **Storage class** | k3s `local-path` | `local-path` on one node; a replicated class (for example Longhorn) for several nodes, set with `storageClass` |
| **Secrets** | generated at first install | the same, plus the LLM key created by hand; for GitOps use sealed secrets or an external secret manager, because of the `lookup` limitation |
| **Images** | built locally, loaded with `k3d image import` | pushed to a registry, `imagePullPolicy: Always`, immutable tags per release |
| **Backups** | `scripts/backup.ps1` by hand | a scheduled job and an off-cluster copy (not built) |

## 9. Known limits

* One replica of every component. The gateway is stateless on purpose, but running more than one replica was never
  tested, and two things are per process: the chat rate limiter and the server status cache.
* The Woo MCP server, the stores' volumes and the databases are single points of failure.
* No metrics endpoint, no tracing.
* Sessions to upstreams are opened per call (no pooling).
* The notes server keeps its notes in memory and must stay at one replica.
* MariaDB and Postgres use minor-version tags. Base images (`python:3.12-slim`, `node:lts-alpine`,
  `nginx-unprivileged:alpine`) are not pinned to digests.
* No database migration tool, no scheduled backups, no restore automation.
* The MCP endpoint has no per-key rate limit (only the chat has one).
* Local traffic is HTTP.
